# 改生产配置前先备份并停服务

**结论**：改生产环境配置或数据库前，先确认有完好备份；改动时遵循「停服务 → 覆盖 → 起服务」，避免写入竞态。

## 为什么

2026-08 事故：还原一台服务器的面板数据库时，没有先停服务就直接覆盖，导致数据库在写入过程中被覆盖，变成 malformed，代理进程宕机。幸好有一份完好的备份才救回，但已属重大事故。

教训：还原/覆盖不是零风险动作。只要有进程在读写那个文件或库，覆盖就会触发写入竞态，把数据弄坏。

## 怎么做

**改前留底**：
```bash
cp <配置文件> <配置文件>.bak          # 文本配置：留一份当前态
docker exec <db容器> <备份命令>        # 数据库：先导出一份
```

**改时停写**：
```bash
systemctl stop <服务>                  # 或 docker stop <容器>
# 此时再覆盖文件 / 导入备份
systemctl start <服务>                 # 起服务
```

**改后验证**：
```bash
systemctl status <服务>                # 或 docker ps 看 running
<看日志命令> | tail -20                # 确认无报错再对外开放
```

涉及多容器（Web + DB）时，先停应用层，再停/动数据库，顺序别反。

## 反例

- 直接还原数据库不先停服务 → 写入竞态，库损坏。
- 还原前没确认备份完好 → 失败没有退路，只能认栽。
- 改完不验证状态就以为好了 → 实际服务起不来，用户先发现。
- 只备份了配置没备份数据库 → 配置能回，数据回不来。
