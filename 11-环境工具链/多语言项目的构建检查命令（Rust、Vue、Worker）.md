# 多语言项目的构建检查命令（Rust、Vue、Worker）

**结论**：接手一个仓库，先查它有哪几种语言，再逐层配检查闸门。**不存在一套命令打天下** —— 尤其要小心"纯 JS 项目根本没有类型检查这一层"。

谁需要看这条：接手多语言仓库、不知道改完该跑哪些检查的人。

---

## 一、各语言该跑什么

| 语言 / 层 | 检查命令 | 关键点 |
|---|---|---|
| **Rust** | `cargo fmt --check` → `cargo check` → `cargo clippy --all-targets -- -D warnings` → `cargo test` | 静态检查**只覆盖当前编译目标**，换个平台要重跑。详见 [Rust 与 Tauri 后端改动怎么验证](../03-桌面与移动端/Rust%20与%20Tauri%20后端改动怎么验证.md) |
| **前端 Vue / TS** | `npm run build`（必须包含类型检查） | 打包器会直接剥掉类型，不单独跑类型检查的话，类型错能过本地，在部署阶段才炸 |
| **Node 后端（TS）** | `tsc -p tsconfig.json` | — |
| **Node 后端（纯 JS）** | 干跑部署，例如 `npx wrangler deploy --dry-run` | **没有类型检查这一层** |

---

## 二、最容易踩的一条：纯 JS 项目没有类型检查

纯 JS 的 Worker / 脚本项目里：

- 没有类型检查，写错了只能靠跑
- **而且不能写类型注解** —— 写了会直接构建失败（报 `Unexpected '>'` 这类语法错）
- 需要标注类型时用 JSDoc 注释

**推论**：别对一个纯 JS 项目说"跑一下类型检查就行"，它没这一层。

---

## 三、产物也要验

跑完检查不算完，产物本身要验：

| 产物 | 怎么验 |
|---|---|
| 安卓包 | 签名验证（期望通过）；解开看 `lib/` 里只含目标架构 |
| 前端产物 | 看压缩产物（`.gz` / `.br`）生成了没 |

---

## 四、避坑表

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 以为所有项目都能跑类型检查 | 纯 JS 项目里这条命令根本不存在 | 先查仓库有哪几种语言 |
| 只跑打包命令 | 类型错被打包器剥掉，部署阶段才炸 | 显式跑类型检查 |
| 静态检查只跑一个平台 | 其他平台的代码根本没被检查 | 分目标各跑一遍 |
| 在纯 JS 项目里写类型注解 | 构建直接失败 | 用 JSDoc |
| 检查全绿就交付 | 产物本身可能是坏的 | 查签名、查架构、查压缩产物 |

---

## 五、锁文件：本地能过、换台机器就挂的头号原因

检查全绿但另一台机器（或 CI）上构建失败，第一顺位不是报错的那段代码，而是**依赖版本不一样**。

| 要查的 | 怎么看 | 判定 |
|---|---|---|
| 锁文件提交了吗 | 仓库里有没有 `package-lock.json` / `pnpm-lock.yaml` / `Cargo.lock` | 没提交 = 每个人装的版本都可能不同 |
| 锁文件没改动吧 | `git status` 看它有没有被"顺手"更新 | 只是装了个包就改了一大片 = 依赖树整体被升过 |
| 两台机器装的一样吗 | 各自跑一次"列出已安装版本"，逐行比对 | 有差异就是它 |
| 该用哪个包管理器 | 锁文件是哪个管理器建的，就用哪个 | 用 npm 去装 pnpm 项目的依赖，必然不一致 |

做法：

- 锁文件**跟着代码一起提交**，改了依赖的提交和锁文件改动放在同一个提交里。
- 换机复现问题时**先对齐依赖**：按锁文件做一次干净的安装，再谈别的。
- 不要用"删掉锁文件重新装"来"修"构建失败 —— 那是换了一棵依赖树，问题从"可复现"退化成"看运气"。

## 六、先核实目录里到底有什么，再开工

**结论**：动手前**列出目标目录的实际文件**数一遍；用户口述的路径、文档里抄的路径、名字像的那个目录，都可能是错的。

**实测（2026-10-15）**：用户给了一个"完整源码"的路径，那里只有 3 个文件；真正的源码在另一个同名目录里，约 140 个文件。项目照着错的目录建了一半才发现。

| 做法 | 命令 |
|---|---|
| 数文件个数 | `find <目录> -name "*.ts" \| wc -l` |
| 看顶层结构 | `ls -la <目录>` |
| 别信名字 | 名为 `readable-src` 的目录不一定就是那份完整源码 |

发现路径不对，**先说清楚再改**，不要把已建的东西擅自搬走。

## 七、生成代码的机器校验：覆盖率 + 类型 + 构建，三道闸门

**结论**：一大票 AI 并行写代码时，**"每个代理都说自己写完了"不算验收**。要用**可重复的机器判据**验收，并且先确认这些判据本身是真的在检查东西。

**实测（2026-10-15，147 个原版模块移植到 TypeScript）**：

| 闸门 | 命令 | 这一轮暴露的问题 |
|---|---|---|
| 类型检查 | `npx tsc --noEmit` | 基线是 exit 0，但**先要证明它真的检查了源码**（见下一条） |
| 构建 | `npm run build` | 比 tsc 更严：`.vue` 文件 tsc 根本不解析 |
| 覆盖率 | 自写脚本：按每个文件头注释里的「来源模块 ID → 原版路径」对齐，逐文件判定"已移植 / 未移植" | 报告 78.9%（116/147），并列出未覆盖清单 |

覆盖率的**已知误差**要写进文档：如果新文件的头注释格式和脚本预期不一致（多行列表 vs 单行），已移植的文件会被判成"未覆盖"。实测出现过同一批文件"报告说写了、覆盖率说没覆盖"，需要人工核实。

**教训**：

1. 验收脚本要**故意制造一个失败样本**跑一次，确认它会报错 —— 一个永远返回"全部通过"的脚本等于没有。
2. 覆盖率脚本的判定依据要**写进文档**（哪一行注释、什么格式），否则接手的人会把误报当成事实。
3. 并行代理的验收**只看机械输出**，「我已完成」的自述不作数。详见 [怎么给 AI 派活](../01-AI 协作/怎么给%20AI%20派活.md)。

## 八、脚手架的默认 tsconfig 可能一个源码文件都不检查

**结论**：用脚手架（Plasmo / 各种 `create-*`）起项目后，**先验证类型检查真的在看你的源码**，否则 `tsc --noEmit` 会"零错误"退出，但它一个源文件都没查。

**实测（2026-10-15，Plasmo + Vue3 + TS）**：

| 现象 | 证据 |
|---|---|
| `tsconfig.json` 的 `include` 默认只有 `[".plasmo/index.d.ts"]` | 等于只检查自动生成的类型声明 |
| `tsc --noEmit` 零错误退出 | 看起来一切正常 |
| `tsc --noEmit --listFiles` 里项目源文件数为 **0** | **所有类型检查结论都是假的** |

**修法**：把 `include` 补成 `.plasmo/index.d.ts` + `**/*.ts` + `**/*.vue`；实测构建命令**不会覆盖** `include`，改一次是持久的。

**配套两个坑**：

- tsc **不解析 `.vue` 文件内容**，改完 `.vue` 必须跑一次完整构建才算验证过；
- Vue 的 `*.vue` 需要**全局 shim**（放在无 import/export 的 `.d.ts` 里）；放进带 export 的 `.ts` 会报 TS2664（模块增强非法）。

## 九、打包产物里中文会被转成 unicode 转义

**结论**：构建工具常把非 ASCII 字符转义成 `\uXXXX` 这种形式，**在打包产物里 grep 中文关键词会一律搜不到**，很容易误判「代码里没有这个功能」。

**做法**：

1. 在**源码**里搜中文字面量，不在产物里搜；
2. 必须在产物里搜时，先做一次反转义再搜（`re.sub(r"\\u([0-9a-fA-F]{4})", ...)`），或改搜英文标识符、接口路径。

**实测**：产物里 5 个 bundle 中文全部是转义形式，不反转义时搜「会员/额度」零命中；反转义后 98 处命中，直接改变了结论。
