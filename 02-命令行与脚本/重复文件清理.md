# 重复文件清理

安全地把重复文件找出来并处理掉。核心原则：**先筛后算，先看后删**。

用户环境实测：有音乐文件重复清理的 Python 和 Go 两个实现版本。

---

## 一、为什么不能直接全文件哈希

直接对每个文件算一遍哈希最简单，但最慢——100GB 的文件要全读一遍，磁盘 IO 是瓶颈。

分级筛选的思路：**用便宜的条件先砍掉绝大多数文件，只对剩下的一小部分做昂贵的计算。**

| 阶段 | 操作 | 成本 | 能砍掉 |
|---|---|---|---|
| 1 | 比文件大小 | 几乎为零（只读元数据） | 大部分 |
| 2 | 比文件头尾的部分哈希 | 低（每个文件只读几十 KB） | 又一批 |
| 3 | 比全文件哈希 | 高（整个文件读一遍） | 最终确认 |

100GB 音乐库走完前两级，候选文件从全量降到几百 MB 量级——只有最后这一步需要读完整文件。

## 二、怎么做

### 第 1 步：按大小分组

大小不同的文件必然不同，直接排除。只保留大小相同的组。

Python 实现：

```python
import os
from collections import defaultdict

def group_by_size(root):
    groups = defaultdict(list)
    for dirpath, _, filenames in os.walk(root):
        for name in filenames:
            path = os.path.join(dirpath, name)
            try:
                groups[os.path.getsize(path)].append(path)
            except OSError:
                pass
    return {size: paths for size, paths in groups.items() if len(paths) > 1}
```

`os.walk` 比 `glob` 递归省内存——它是生成器，不会一次性把整个目录树读进内存。

### 第 2 步：部分哈希再砍一刀

对每个候选读头尾各 64KB 算哈希。头尾相同再进下一步。

```python
import hashlib

def partial_hash(path, chunk=65536):
    h = hashlib.md5()
    size = os.path.getsize(path)
    with open(path, 'rb') as f:
        h.update(f.read(chunk))
        if size > chunk * 2:
            f.seek(-chunk, os.SEEK_END)
            h.update(f.read(chunk))
    return h.hexdigest()
```

先算部分哈希这步对大文件（音乐、视频）提速极明显——不同歌曲几乎不可能头尾都相同。

### 第 3 步：全文件哈希确认

```python
def full_hash(path):
    h = hashlib.sha256()
    with open(path, 'rb') as f:
        for block in iter(lambda: f.read(1024 * 1024), b''):
            h.update(block)
    return h.hexdigest()
```

`iter(lambda: f.read(...), b'')` 这种写法是分块读，不会把 2GB 的文件一次性读进内存。

### 第 4 步：先干跑，看清单

**这一步不能省。** 删之前把清单打出来，人工扫一眼：

```python
for digest, paths in duplicates.items():
    print(f"--- 重复组（{len(paths)} 个）---")
    for p in paths:
        print(f"  {p}")
```

## 三、选哪个哈希

| 算法 | 速度 | 碰撞概率 | 什么时候用 |
|---|---|---|---|
| MD5 | 快 | 理论存在，实际检测重复文件够用 | 文件去重（推荐） |
| SHA-256 | 慢约 2-3 倍 | 极低 | 要求严格、或内容涉及校验 |

纯去重场景 MD5 完全够——它是用来找相同文件，不是防恶意伪造。100GB 库用 SHA-256 会明显多花时间，收益为零。

## 四、删之前：三种处理策略

| 策略 | 做法 | 什么时候用 |
|---|---|---|
| **移到隔离目录**（最安全） | 剪切到一个临时文件夹 | 拿不准，想留后悔药 |
| **硬链接** | 多个路径指向同一份数据 | 想保留目录结构，又要省空间 |
| **直接删** | 保留一个，删其余 | 已确认清单无误 |

推荐第一种：先移走，跑一周没问题再真删。删了就找不回来了。

保留哪一个的判断依据：

| 依据 | 说明 |
|---|---|
| 路径最短 / 层级最浅 | 通常在更规整的位置 |
| 修改时间最早 | 认为是最初导入的那份 |
| 文件名最规范 | 另一个可能是 `xxx (1).mp3` 这种 |

**不要自动选，把清单打出来让人看。** 音乐库里 `track.mp3` 和 `我的音乐/track.mp3` 内容一样，但用户在意保留哪个。

## 五、Python 还是 Go

| | Python | Go |
|---|---|---|
| 开发速度 | 快，几行搞定 | 慢一些 |
| 首次扫描 100GB | 慢（解释执行 + GIL） | 快 5-10 倍（编译执行 + 原生并发） |
| 并发写起来 | 麻烦（IO 密集用线程池，CPU 密集受 GIL 限制） | 简单（goroutine 天然并发） |
| 分发 | 要装 Python | 编译成单个 exe，双击就跑 |

**跑一次的小任务用 Python，要反复跑或给别人用就上 Go。**

哈希计算是 CPU 密集的，Python 的 GIL 让多线程跑不满多核；Go 的 goroutine 能真正吃满 CPU。这就是同一个功能写两版的理由。

## 六、常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 跳过干跑直接删 | 误删了其实不同的文件 | 必须先看清单 |
| 用 `os.path.getsize` 之外的方式比大小 | 慢 | 只读元数据，不要读文件内容 |
| 一次性 `f.read()` 整个大文件 | 2GB 文件直接把内存吃光 | 分块读 |
| 只看文件头不算尾 | 同名不同内容的文件误判为重复 | 头尾都算 |
| 删完才发现硬链接/软链接指向它 | 别的地方打不开了 | 删之前确认没有其他引用 |
| 用 MD5 做安全校验 | 不安全 | 那是另一个场景，用 SHA-256 |
| 扫描目录包含自身输出目录 | 无限循环或把结果文件也算进去 | 输出目录放扫描范围外 |
