# 稳妥执行任务：少用内联命令，多做「文件化脚本 ＋ 双击入口」

**结论**：凡是**需要反复执行**的动作，都不要让用户敲命令 —— 写成脚本文件（`.vbs` / `.bat` / `.py`）＋ 桌面快捷方式，双击即用。AI 自己执行任务时，**长命令、含引号/中文/JSON/路径的命令，先落盘成脚本再执行**，不要内联在一条命令里。

## 一、为什么内联命令不可靠

三种 shell 的转义规则互不相同，嵌套调用必然出错：

| shell | 转义符 | 典型坑 |
|---|---|---|
| `cmd` | `"` | 引号内的 `%` 会被当变量展开 |
| PowerShell | `` ` `` | `"` 与 `` ` `` 混用、`$` 被当变量 |
| bash | `\` | 路径 `/d/...` 传给 Windows 程序会变成 `d:\d\...` |

再叠加**版本差异**与**编码差异**，同一条命令换台机器/换个终端就可能失败：

- Windows PowerShell **5.1** 不支持 `&&`、`||`、`??`、`?.`，也**没有** `-Environment` 参数（实测报 `A parameter cannot be found that matches parameter name 'Environment'`）
- `Set-Content` / `Out-File -Encoding utf8` 会写 **BOM**（`EF BB BF`），下游解析器普遍拒收：uv 报 `Failed to parse environment file at position 0`（**静默丢弃整份配置**）、Python `json.load` 报 `Unexpected UTF-8 BOM`
- `.bat` 里写中文会被按字节切错（`'的' is not recognized as an internal or external command`）

### 1.1 同一个「写文本」，三种编码（实测字节对照）

Windows PowerShell 5.1 下用不同写法写同一段文本，产出完全不同：

| 写法 | 首字节 | 结果 |
|---|---|---|
| `Set-Content` | `6B 65 79`（`key`） | UTF-8 无 BOM（**跟随系统 ANSI 代码页，不是固定 UTF-8**） |
| `Out-File` | `FF FE` | **UTF-16LE** |
| `Out-File -Encoding utf8` | `EF BB BF` | **UTF-8 带 BOM** |
| `[System.IO.File]::WriteAllText($p,$t,(New-Object System.Text.UTF8Encoding($false)))` | 直接内容 | ✅ 确定的 UTF-8 无 BOM |

**结论**：要写配置文件，只用最后一种写法（或编辑器/工具本身的写文件 API）。

### 1.2 BOM 的真实后果（已完整复现）

给 `.env` 加上 BOM 后跑 `uv run --env-file .env`：

```
warning: Failed to parse environment file `.env` at position 0: ﻿FOO=bar
```

实测结果 **`FOO = None`** —— 变量根本没读进来，而**无 BOM 版本正常**（`FOO = bar`）。

最危险的地方：**服务照常启动、`/health` 照常返回 ok**，只是配置全没生效。本项目的实际表现是「网关无鉴权裸奔」，排查了半天才发现是 BOM。

⚠️ **解析器容忍度不一致**：`python-dotenv` 能容忍 BOM（实测解析正常），`uv` 不能。**「某个库能读」不能证明文件没问题。**

**外部同源案例（2026-10-08 检索，证明这是跨平台通病）**：

- [Windows PowerShell 5.1 `Out-File -Encoding utf8` 写 BOM 破坏 post-commit hook 重建（WinError 123）](https://github.com/Graphify-Labs/graphify/issues/3028)
- [`.env` 里的 UTF-8 BOM 静默丢掉第一个键](https://github.com/NousResearch/hermes-agent/issues/65123) 与 [修复 PR #65248](https://github.com/NousResearch/hermes-agent/pull/65248)
- [`Get-Content -Raw` 的 UTF-8 陷阱与 PS 5.1 BOM 安全往返](https://github.com/deftai/directive/issues/236)
- [官方 about_Character_Encoding](https://learn.microsoft.com/zh-cn/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-7.7)

### 1.3 不可见字符：看起来一样，解析必挂

零宽空格（U+200B）、BOM 字符本身（U+FEFF）、不间断空格（U+00A0）、全角空格与全角引号 —— **肉眼完全看不出来**，混进配置或脚本就会失败。

实测：`PORT=8787` 末尾混入一个零宽空格后，字节数从 9 变成 **12**（末端 `E2 80 8B`），屏幕上显示的一模一样。

**做法**：

1. 配置/脚本**只用 ASCII 可见字符**，注释也尽量；
2. **从网页/聊天窗口复制来的命令必须重打一遍**，或先验字节；
3. 怀疑时用 `Format-Hex 文件` 或 `[System.IO.File]::ReadAllBytes()` 看首尾字节；
4. `.gitattributes` 或提交前检查，避免 BOM 混进仓库。

## 二、正确做法（按优先级）

### 1. 首选「文件化 ＋ 双击」

给用户的入口**永远是双击**，不是命令行。已验证可行的组合：

| 形态 | 特点 |
|---|---|
| `.vbs` ＋ `wscript.exe` 快捷方式 | **完全无窗口**；可隐藏拉起服务、轮询健康检查、就绪后自动开浏览器 |
| `.bat` ＋ 快捷方式 | 有窗口（能看进度）；正文**只用 ASCII** |
| `.py` ＋ `.bat` 包一层 | bat 只负责 `chcp 65001` 与调 Python，**中文全部由 Python 输出** |

#### 关于 `.bat` 里的中文：`chcp` 是治不了的

**结论**：`.bat` 正文**只用 ASCII**，中文交给被调用的脚本输出。

**为什么 `chcp 65001` 没用**：Windows 解析 bat 时是按**当前代码页把字节切成 token** 的，中文是多字节字符，解析器会把它当**命令边界**切开 —— 所以 bat 里写中文 `echo` 不只是乱码，**会直接被拆成多条命令报错**：

```
'的' is not recognized as an internal or external command
```

`chcp 65001` 改的是**控制台显示的编码**，改不了 bat 自己被解析的方式。而 bat 调用 Python 时，`print("中文")` 走的是 **Python 自己的 stdout 管道，不经过 cmd 的 bat 解析器** —— 所以「bat 里中文报错、Python 打印中文正常」并不矛盾。

**标准模板**：

```bat
@echo off
chcp 65001 >nul
cd /d "%~dp0"
"<你的 python 路径>" <你的脚本>.py --status
echo.
pause
```

要点：`cd /d "%~dp0"` 切到 bat 所在目录（双击时才找得到脚本）；python 写绝对路径（bat 是文件，不存在变量失效问题）；`pause` 防止双击时窗口一闪而过；**中文不出现在 bat 里**。不知道 python 在哪：`where python`。

**兜底（中文必须写在 bat 里）**：存成 **UTF-8 BOM**。不带 BOM 时 Windows 按系统 ANSI 代码页解析中文注释，整片炸成 `'xxx' 不是内部或外部命令`；带 BOM 就能正确识别为 UTF-8。实测（2026-08-15）：一个启动脚本的中文注释整片乱码，改存 UTF-8 BOM 后正常。

⚠️ 注意：在确定系统代码页是中文的环境下，不带 BOM 也可能正常；换个系统就炸 —— **要么纯 ASCII，要么加 BOM，别赌**。

### 2. AI 自己执行：能落盘就别内联

长命令、含引号 / 中文 / JSON / 特殊路径的命令 → **先写成脚本文件，再执行该文件**；临时脚本用完即删。

### 3. 长驻服务必须脱离调用者的会话

**踩过的真实事故**：在 AI 会话里起的服务进程，会话任务被取消时被**连带杀死**，用户正在用的服务当场断线。

规矩：

- 长驻服务由**用户双击**或**独立窗口**启动；
- 需要 AI 代起时，走 `explorer.exe` 派生（`explorer.exe "启动.vbs"`）或计划任务 —— 实测父进程退场后成为独立进程；
- **绝不取消可能包含该服务的任务** —— 先查端口占用 PID 是否在该任务树里。

## 三、写脚本的硬性纪律

| 项 | 规则 |
|---|---|
| `.vbs` 变量 | `Option Explicit` 下**逐个 `Dim`**，漏一个就报「变量未定义」（实测 `800A01F4`） |
| `%comspec%` | 用 `sh.ExpandEnvironmentStrings("%comspec%")` **显式展开**，`WshShell.Run/Exec` 不保证展开 |
| 编码 | `.vbs` → **UTF-16**；`.bat` → **纯 ASCII**（必须写中文则 UTF-8 BOM，见「二、1」下的 `.bat` 中文小节）；`.env`/YAML/JSON/`.py` → **UTF-8 无 BOM** |
| 交付前 | **先 `cscript //nologo 文件.vbs` 试跑**验语法（错误打到 stdout，能当场发现）——别把没验过的脚本直接丢给用户双击 |

## 四、样板：无窗口启动本地服务（VBS 骨架）

```vbs
Option Explicit
Dim sh, fso, comspec, url, env, cmd
Set sh = CreateObject("WScript.Shell")
Set fso = CreateObject("Scripting.FileSystemObject")
comspec = sh.ExpandEnvironmentStrings("%comspec%")
url = "http://127.0.0.1:<端口>"

If GatewayUp() Then           ' 已在运行 → 直接开面板
  sh.Run url & "/dashboard", 1, False
  WScript.Quit 0
End If

Set env = sh.Environment("PROCESS")   ' 注意：env 必须在顶部 Dim
env("NO_PROXY") = "localhost,127.0.0.1,.cn"

cmd = comspec & " /c cd /d ""<项目目录>"" && ""<可执行文件>"" <参数> 1>>""<日志>"" 2>&1"
sh.Run cmd, 0, False                  ' 0 = 隐藏窗口

Dim i
For i = 1 To 60                       ' 轮询就绪
  WScript.Sleep 1000
  If GatewayUp() Then
    sh.Run url & "/dashboard", 1, False
    WScript.Quit 0
  End If
Next
MsgBox "启动超时，请查看日志", 48, "启动失败"
WScript.Quit 1

Function GatewayUp()
  Dim h
  On Error Resume Next
  Set h = CreateObject("MSXML2.ServerXMLHTTP.6.0")
  h.setTimeouts 1000, 1000, 2000, 3000
  h.Open "GET", url & "/health", False
  h.Send
  GatewayUp = (Err.Number = 0 And h.Status = 200)
  On Error GoTo 0
End Function
```

配套：桌面快捷方式指向 `wscript.exe`，参数写 `"<你的>\启动.vbs"`。

## 五、一条被推翻的推断（别当真）

曾流传「`Start-Process` 在 Git Bash 派生会话里会因环境变量同时有 `Path` 与 `PATH`（重复键）而崩溃」。**2026-10-08 实测不成立**：`Start-Process`（含中文 + 空格路径、`-WindowStyle Hidden -PassThru -Wait`）全部正常，从 Git Bash 调 `powershell -NoProfile -Command` 也正常返回。

**教训**：没验证的推断不要写成结论 —— 写进记忆后会被当成事实传播，误导后续排查。
