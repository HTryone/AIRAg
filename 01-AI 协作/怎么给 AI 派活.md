# 怎么给 AI 派活

**结论**：派一个非琐碎的活，必须同时说清三件事 —— **目标、边界、验收标准**。缺一件，AI 就会自己脑补，脑补的部分八成不是你要的。

## 为什么

用户多次纠正过这类问题：让改 A，AI 顺手把 B 也改了；让优化，AI 顺手重构了。根因不是 AI 不守规矩，是任务本身没说清边界，AI 只能猜。

猜错了再返工，比一开始多说三句话贵得多。

## 怎么做

派活时用这个格式：

```
目标：把 X 从 A 提到 B
边界：只改 <哪些文件/模块>，其他一律不动
验收：怎么算做成了（可观测的结果）
禁止：明确列出不许做的事
```

四项都要具体：

| 项 | 说清什么 | 反例（太含糊） |
|---|---|---|
| 目标 | 量化，能测 | "优化一下速度" |
| 边界 | 具体到文件 / 模块 | "改改相关的地方" |
| 验收 | 跑一次能看到的結果 | "好用就行" |
| 禁止 | 不许重构、不许顺手修别的、不许动数据 | 不写 |

### 完整例子

```
目标：把上传平均速度从 3 MB/s 提到 6 MB/s
边界：只改 src/transfer/ 下的分片与并发逻辑，不动加密和界面
验收：连续跑 3 次，平均速度稳定在 6 MB/s 以上，且断点续传仍正常
禁止：不要重构目录结构，不要顺手修别的 bug，不要改线上配置
```

## 什么时候可以不用这么正式

改动可逆、一眼能看明白的琐碎任务，直接说就行。比如"把版本号改成 1.2.3"。

判断标准：**AI 有可能做多或做偏的，就要说清边界**。见 [先给方案再动手](先给方案再动手.md)。

## 反例

```
"把上传优化一下"
```

没有目标（提到多少算成）、没有边界（改哪）、没有验收（怎么算成）、没有禁止（不许动什么）。AI 只能自行发挥，结果必然是要么改少了，要么改多了。
