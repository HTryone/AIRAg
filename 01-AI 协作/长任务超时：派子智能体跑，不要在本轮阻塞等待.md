# 长任务超时：派子智能体跑，不要在本轮阻塞等待

**结论**：要跑十几分钟以上的活，派给子智能体后台跑，主线程立刻回报并继续别的；主线程只做"只有它能做的"和"几秒能查完的"。

## 为什么

主线程阻塞在一条长命令上时，用户既看不到进度，也插不进话 —— 想改需求、想追问、想中止，全得等你这条命令结束。反过来，拿几分钟的小事去外派，主线程也只能干等对方交卷，同样插不上话。

所以判断标准不是"活大不大"，而是**两种浪费哪个更贵**：

| 做法 | 代价 |
|---|---|
| 小事外派 | 主线程空等 + 多一层转述 |
| 长活自己在主线程跑 | 用户被锁在门外十几分钟，出问题只能等 |

## 怎么分

| 现状 | 做法 |
|---|---|
| 一条命令、查个配置、看段日志、读一个文件 —— **几分钟内出结果** | **主线程直接做，边做边报** |
| 多台机器 / 多个目录 / 大规模扫描，**可并行** | 拆给多个子智能体，范围互斥，各自后台跑 |
| 长时间自主跑、中途不需要用户介入 | 派给一个子智能体后台跑 |
| 要拍板、要动生产、要用凭据 | **必须主线程**，不外派 |

## 派出去了，主线程做什么

1. 交代验收标准（怎样算成）和范围（**不许做什么**）。
2. 立刻回报："已在后台开始，预计要看哪些产出"，把控制权交回用户。
3. 之后**按产出文件判断进度**（数量 / 大小 / 时间戳），不空等交卷；卡住就催办或拆小。
4. 交卷后**自己再取一次关键数字比对**，不轻信"已完成"。

## 反例

- 坐在主线程里等 20 分钟的批量任务，用户中途改需求，只能推倒重来。
- 反过来，查一个配置项也非要派个子智能体，用户等了两分钟，拿到一句本该一句话答完的话。
- 派出去了不管，等对方交卷才发现范围划重了，两个子智能体改同一批文件。

## 止损线

派活前先问一句：**这件事要是卡住了，用户还能不能插话？** 不能，就别在主线程干等。
