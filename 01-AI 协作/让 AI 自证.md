# 让 AI 自证

**结论**：AI 给出的每一条关于现状的结论，都必须能指出**出处**——代码就给文件路径和行号，运行状态就给命令加实际输出。指不出出处的，直说"没有证据"，不许猜。

## 为什么

用户反复追问"你确定有没有问题吗""源码都在仓库里面"，根因是 AI 会凭印象下结论。印象会过期——文件早就改过了，AI 还按几轮前的记忆回答。

这类错误最危险的地方在于：**它听起来很确定**。一句"应该是缓存没清"，用户可能就照着去改，改完发现根本不是。

## 怎么做

按结论的类型配出处：

| 结论类型 | 必须附的出处 |
|---|---|
| 代码现在长什么样 | 文件路径 + 行号（`src/a/b.ts:142`） |
| 某个配置是什么值 | 配置文件路径 + 那一行的内容 |
| 现在运行状态如何 | 执行的命令 + 实际输出，不能只写结果 |
| 某个操作有没有生效 | 前后两次读数的对比 |
| 历史上有过什么事 | 日期 + 当时的原始记录 |

拿出处的方式：**实际去读、去跑**，不靠记忆。

```bash
# 说某个文件有这段代码之前，先读它，引用时带行号
# 说某个服务在跑之前，先查，把输出贴出来
```

### 查不到的时候

直接说"没查到证据，无法确认 X，需要你提供……"。

这句话不是示弱，是有效信息——它告诉用户这件事还没被证实，别拿它做决策。

## 交付前自检

结论写完，逐条问自己：

- [ ] 这条结论我能指出是从哪个文件 / 哪条命令来的吗？
- [ ] 出处是这一轮实际读到的，还是凭印象写的？
- [ ] 有没有用"应该 / 大概 / 按理说"糊过去的地方？
- [ ] 我引用的行号，是我刚读到的还是上次读的？

任何一条答不上来 → 回去查，查不到就明说。

## 反例

```
"这个接口应该走的是缓存，可能是缓存没清导致的。"
```

三个问题：没有文件路径、没有实际读到的值、用了"应该"和"可能"。

正确说法：

```
"src/api/query.ts:87 走了缓存分支，缓存键是 userId。日志里这次请求的 userId 是 10042，
缓存命中记录里没有这个键 —— 确认是没命中，不是缓存没清。"
```

或者查不到时：

```
"没有找到缓存相关的日志输出，无法确认这次请求有没有走缓存。需要开启 debug 日志再跑一次。"
```

## 七、证据链：一次根因，别停在一手证据

**结论**：对同一件事，**至少要两条互不依赖的证据**；只有一条时，先问「还有谁会影响它」，把排除项也做成证据。

**实测（2026-10-18）**：Windows 沙箱给工作区授权写权限时报 `SetNamedSecurityInfoW failed (Win32 5): grantWrite`，所有 shell 调用全挂。

| 环节 | 证据 | 结论 |
|---|---|---|
| 一手 | 报错码 Win32 5 = 拒绝访问 | 写入权限被拒 |
| 外部事件 | 同一时段杀毒软件把该目录下的可执行文件隔离 | 环境被外部软件动过 |
| **旁证** | 读取类工具（只读列举/读文件）**全部正常** | **不是文件坏了、不是路径错，而是写权限那一条被挡** |

第三条才是关键：它把「文件损坏 / 路径不对 / 沙箱坏了」三种可能一次排除掉。

**做法**：

1. 拿到一手报错后，**先做排除实验**：只读操作行不行？换个目录行不行？换个账号行不行？
2. 排除结果写进结论里（「只读正常、写被拒」比「报错 5」信息量大得多）。
3. 只有一条证据、做不出排除实验时 —— 明说「只有这一条证据」，别把它包装成定论。

**反例**：看到 `Win32 5` 就断言「杀毒软件干的」，然后去折腾杀软设置 —— 没有旁证，方向全靠猜。
