# 文档架构先锁死、新增只追加不重构

**结论**：一套长期维护的文档（操作手册、调优手册、记忆库），动手写第一版前先把"文档架构"定死——哪几份文件、各管什么、何时动哪份。定死之后，新内容只追加、不重构、不挪位置、不合并、不删（除非用户明确授权）。

## 为什么

- 证据：一台服务器的运维文档，早期拆成 4 份（security-backup / SERVER-LONGTERM / MEMORY / 调优手册），职责边界没定死，互相交叉。结果反复重写、合并、删文件，光"文档重构"就折腾好几轮，每份都被改过多次，既费时又每次都冒"改丢用户正确内容"的风险。用户原话："你先经过我同意了吗？你就擅自改动？你自己写的红线，你自己为什么不遵守。"
- 根因：架构没尽早定死，边写边调整分工，每次调整都要动多份文件、重排内容。
- 教训：架构是一次性决策，内容才是持续累加的。把"调整架构"和"加内容"混在一起，代价翻倍。

## 怎么做

### 第 1 步：定架构（写之前）

列一张分工表，锁定：

- 哪几份文件
- 每份文件的角色（必读 / 备查 / 日志）
- 什么情况下才动这份文件
- 内容冲突时以谁为准

锁死后把这张表写进某份文件的"文档架构"节，作为以后所有 AI / 人都遵守的契约。

### 第 2 步：加内容只追加

- 新经验 → 新增一个文件，或往对应文件加一节
- 已写的内容 → 不改、不挪、不合并（除非用户明确授权）
- 每份文件留一个"可扩展占位"区（如 `## 待补充` 列表），新东西先丢进去

### 第 3 步：要调整架构必须先报批

删除 / 合并 / 拆分 / 移动文件、新建目录，都**先给用户方案、拿到同意再动**。方案里逐个列出将被删除的文件名、动完是什么样、为什么更好。

> 这条和 [撤销改动必须用户授权](../01-AI%20协作/撤销改动必须用户授权.md) 是同一根红线在不同场景的体现：文档结构调整 = 文件级改动，必须授权。

## 反例

- 写了 4 份职责交叉的手册，发现重叠就合并 → 合并要重排多份，每次都冒改丢风险。
- 用户加了正确内容，重构时顺手"整理"没了 → 用户原话："让你删的你不删，不让你删的全删了。"
- 把"加一条经验"做成"重写整份文档" → 浪费，且破坏已有内容稳定性。
