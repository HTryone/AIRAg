# 大文件传输调优

把上传/下载速度从「能跑」调到「跑满」。这篇讲的是**调参顺序和判定方法**，不是某套万能参数。

用户环境实测（ArkPulse stable-v3，commit a65e889）：4MB 分片 + 24MB 窗口 + 3 路并发 + 50ms ack，平均 5.0MB/s，速度在 4-6MB/s 之间振荡。单流上限 2MB/s。

---

## 一、先搞清四个参数

| 参数 | 是什么 | 调大的效果 | 调大的代价 |
|---|---|---|---|
| **分片大小** | 一个请求发多少数据 | 减少请求次数，摊薄握手开销 | 单片失败重传成本高；内存占用涨 |
| **并发数** | 同时发几路 | 绕开单流速率上限 | 太多会互相抢带宽，反而更慢 |
| **窗口** | 在途未确认的数据总量 | 填满高延迟链路（带宽时延积） | 内存占用涨；丢包时重传量大 |
| **ack 间隔** | 多久确认一次 | 减少确认包开销 | 太大则拥塞控制反应迟钝 |

一句话记：**分片决定单次成本，并发决定能开几条道，窗口决定道上能压多少车，ack 决定多久回一次话。**

它们互相制约，单改一个往往没效果。比如窗口开大但并发只有 1，单流上限照样卡死你。

---

## 二、调参顺序（必须按这个来）

**分片 → 并发 → 窗口 → ack。** 每一步都要测出数字再进下一步，跳步等于白调。

### 第 1 步：定分片大小

起点 4MB，然后二分试探：

| 网络条件 | 建议起点 |
|---|---|
| 国内 / 低延迟 | 4MB |
| 跨境 / 高延迟（>150ms） | 8MB |
| 移动网络 / 易断 | 1-2MB |

判定：分片翻倍后速度没变化 → 说明瓶颈不在这，回到原值，进第 2 步。

### 第 2 步：定并发数

从 1 开始往上加：1 → 2 → 3 → 4 → 6。

**判定标准**：速度不再增长就停在当前值，不要再往上加。ArkPulse 实测加到 3 路就不再涨，第 4 路纯属浪费。

单流被限速时（实测 2MB/s），并发是唯一有效的破局手段——3 路 × 2MB/s 才凑出 5MB/s。

### 第 3 步：定窗口

窗口 ≈ 带宽 × 往返延迟。粗算：

```
窗口(MB) ≈ 速度(MB/s) × 延迟(s)
```

例：5MB/s、延迟 200ms → 窗口约 1MB 才够填满链路。实测用到 24MB 是为了覆盖延迟抖动，不是理论下限。

判定：窗口翻倍速度不变 → 链路没被填满的假设不成立，瓶颈在别处。

### 第 4 步：调 ack

最后动，默认 50ms 起步。只在确认包开销明显（小分片 + 高并发）时才往上调。

---

## 三、怎么判定「调好了」

### 看振荡幅度，别看峰值

记录连续 10 次采样的速度，算最大值和最小值的差：

| 振荡幅度 | 判定 |
|---|---|
| 小于 20% | 稳定，可以收工 |
| 20%-50% | 可用，但有优化空间 |
| 大于 50% | 参数不匹配，继续调 |

实测 4-6MB/s（振荡 40%）属于「可用但没调完」的状态。

**峰值好看没有意义**，用户感受到的是平均速度。7MB/s 峰值配 2MB/s 谷值，体验不如稳定 5MB/s。

### 振荡明显的常见来源

| 现象 | 来源 | 应对 |
|---|---|---|
| 周期性冲高后归零 | 发送端缓冲攒够了一批才发（脉冲式） | 改用流式管道，边读边发 |
| 速度阶梯式下降 | 并发路数互相抢带宽 | 减并发 |
| 前快后慢 | 内存累积，越跑越慢 | 查发送端有没有把数据全读进内存 |

Chrome 向服务端发请求时的缓冲行为会造成第一种脉冲——数据先攒在浏览器缓冲区，攒够一批才真正发出去，看起来就是「冲一下、停一下」。

## 四、止损线

调参是无底洞，必须有停手条件（见 [接口探测要有止损线](接口探测要有止损线.md)）：

| 条件 | 动作 |
|---|---|
| 某个参数两个值测下来差异小于 5% | 认定该参数已到顶，固定下来 |
| 连续 3 轮组合没超过 10% 提升 | 停止，冻结当前配置 |
| 已达成目标速度 | 停止，不要为了更好看继续调 |

**达到可用状态后冻结配置**，把参数连同实测数字一起记下来（像 stable-v3 那样），下次直接复用。

---

## 五、测量方法

没有数字就不要调参。至少要有：

| 指标 | 怎么测 |
|---|---|
| 平均速度 | 总字节 ÷ 总耗时 |
| 瞬时速度 | 每秒采一次已发送字节数，画曲线 |
| 振荡区间 | 采样里的最大最小值 |
| 各阶段耗时 | 分片、加密、发送、确认分别打点 |

**只报一个「平均速度」等于没测**——5MB/s 平均可能是稳定 5，也可能是 2 和 8 交替，后者需要继续调。

浏览器端必须用 `performance.now()` 打点，不能用 `Date.now()`（精度不够）。

## 六、常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 四个参数一起改 | 有效果也不知道是谁的功劳，下次无法复现 | 一次只动一个，测完再动下一个 |
| 只看峰值速度 | 误以为调好了，实际振荡严重 | 看振荡区间和平均值 |
| 把整文件读进内存再分片 | 大文件直接 OOM | 流式读取，读一片发一片 |
| 并发无脑往上加 | 路数互相抢带宽，越加越慢 | 速度不再涨就停 |
| 换网络环境后沿用旧参数 | 跨境/移动的延迟特性完全不同 | 参数绑定网络条件，换环境要重测 |
| 没记录当时的参数组合 | 想回退都不知道回退到哪 | 每版配置连同实测数字一起存档 |
