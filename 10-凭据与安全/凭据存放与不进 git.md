# 凭据存放与不进 git

凭据一旦进 git，就等于公开了。这篇讲凭据放哪、怎么拦住它、漏进去了怎么办。

---

## 一、哪些算凭据

判断标准：**这个值泄露出去，别人能不能冒充你或者花你的钱。**

| 类别 | 例子 |
|---|---|
| 登录密码 | 服务器 root 密码、数据库密码、面板登录密码 |
| 密钥文件 | SSH 私钥（`id_rsa`、`id_ed25519`）、签名 keystore、TLS 私钥 |
| 令牌 | API token、AccessKey / SecretKey、OAuth client secret、bot token |
| 连接串 | 带密码的数据库连接串、带账号密码的 URL |
| 配置文件 | `.env`、`config.local.*`、含上面任意一项的 yaml / json |

不带密码的主机名、端口号、公开 API 地址**不算**凭据，可以正常提交。

---

## 二、凭据存哪

| 位置 | 放什么 | 通用做法 |
|---|---|---|
| 本机 | 密码、token | 系统凭据管理器；**不要**明文写进脚本和文档 |
| 本机 | SSH 私钥 | 家目录下的 `.ssh`，权限设成只有自己能读 |
| 脚本项目 | 运行时要读的 token | `.env` 文件 + `.gitignore` 拦掉；同时提交一份 `.env.example`（只有键名没有值） |
| 服务器 | 服务要用的密码 | 环境变量，或只有运行用户能读的配置文件；不要写在命令行参数里 |
| 容器 | 镜像里不能有的密钥 | 运行时注入（环境变量 / secret 挂载），**不要**打进镜像 |

两条硬规则：

1. **凭据和代码分开存** —— 代码进 git，凭据不进
2. **需要凭据的地方留占位** —— `.env.example` 写 `DB_PASSWORD=`，让别人照着填自己的

## 三、.gitignore 怎么写

### 新项目从零加

在项目根目录建 `.gitignore`，按后缀拦比按文件名拦更保险：

```
.env
.env.*
!.env.example
*.key
*.pem
*.p12
*.keystore
*.jks
secrets.*
config.local.*
```

`!.env.example` 是例外规则，把它从上面的忽略里放出来。

### 老项目补

**`.gitignore` 只对还没被 git 跟踪的文件生效。** 已经被跟踪的文件，光加规则没用，必须先从跟踪里摘掉，文件本身留在磁盘上：

```bash
git rm --cached .env          # 摘掉跟踪，本地文件还在
git commit -m "停止跟踪 .env"
```

摘完立刻去改凭据（见第五节）——历史里已经有了。

### 全局兜底

怕某个项目忘了配，可以配一个全局忽略文件，对所有仓库生效：

```bash
git config --global core.excludesfile ~/.gitignore_global
```

内容同上。这是兜底，不是替代项目自己的 `.gitignore`。

## 四、日常检查

提交前扫一遍，看暂存区有没有夹带凭据：

```bash
git diff --cached                # 肉眼过一遍将要提交的内容
```

历史里捞关键字：

```bash
git log -S "你的密码或token片段" --all --oneline
```

有输出 = 历史里有，按第五节处理。

自动化工具：`gitleaks`、`git-secrets`，可以挂在提交钩子上自动拦。

## 五、漏进去了怎么办

核心原则：**进过远程的凭据，一律当作已经泄露，必须轮换。**

清理 git 历史既慢又不彻底（别人可能已经拉走了，镜像站可能已经爬了），轮换才是一步到位。

### 情况一：提交了，还没 push

历史只在本地，可以彻底抹掉：

```bash
git reset --soft HEAD~1     # 撤销提交，改动留在暂存区
git restore --staged .      # 全部撤出暂存区
```

然后把凭据挪到 `.env`、加进 `.gitignore`，再重新提交要提交的部分。

用 `--soft` 不是 `--hard` —— 后者会连改动一起丢。见 [回退用 reset --hard 不用 revert](../05-Git%20与版本控制/回退用%20reset%20--hard%20不用%20revert.md)。

这种情况不用轮换，因为没出过本机。**前提是你能确认没 push 过**，包括没被自动同步工具传上去。

### 情况二：已 push 到私有库

1. **先轮换凭据** —— 生成新的，旧的作废
2. 再考虑清历史：`git filter-repo` 或 BFG 把历史里的那几个文件删掉
3. 清完强制推送，并通知所有协作者重新克隆

顺序不能颠倒。轮换是止损，清历史是打扫，先止损。

### 情况三：已 push 到公开库

**只做一件事：立刻轮换。**

公开库会被自动爬取，从提交到被爬走通常只有几分钟。不要花时间清理历史——删了也没用，当作已经泄露处理。

轮换完再回头补 `.gitignore` 和检测手段。

## 六、避坑表

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 凭据写进脚本再提交 | 直接进历史 | 脚本读环境变量或 `.env` |
| 密码写在命令行参数里 | 进 shell 历史，还能被 `ps` 看到 | 用交互式输入或环境变量 |
| 凭据写在 URL 里（`https://用户:密码@主机`） | 进访问日志、代理日志 | 用单独的认证头或配置文件 |
| 以为删掉文件就安全了 | 历史里还在 | 按第五节分情况处理 |
| `.gitignore` 加了但文件已被跟踪 | 规则无效，照样提交 | 先 `git rm --cached` |
| 截图 / 日志里带着 token 一起发出去 | 间接泄露 | 发之前打码 |
| 提交前不看 diff | 夹带进去都不知道 | 提交前过一遍 `git diff --cached` |
| 图省事把 `.env` 传进镜像或打包进产物 | 分发到每台机器上 | 运行时注入 |
