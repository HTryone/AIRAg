# 改动范围必须和授权一致

**结论**：用户授权改 A，就只动 A。顺手把 B、C 一起"优化"了，即使改对了也是越界。

## 为什么

用户反复强调的约束，原话级别：

- 「仅修改 `.workbuddy/memory/manual` 目录下文件，非授权不动 `src/` 业务代码」
- 「任何代码变更需用户明确授权，且**范围必须一致**」
- 「偏好最小范围变更（如仅改 `install.sh` 而非同步修改文档）」

具体表现：用户说"改一下 `install.sh`"，我顺手把对应的 README 也同步更新了。改的内容没错，但用户不认——他要的是「只改 install.sh」这个**范围**，不是「把相关的地方都改好」。

三个真实场景：

| 用户授权 | 我多做了什么 | 结果 |
|---|---|---|
| 改 `install.sh` | 同步更新了文档 | 被要求回退文档改动 |
| 改知识库拆分粒度 | 顺手调整了目录结构 | 被批评"你先经过我同意了吗" |
| 排查某功能 | 顺手重构了相关代码 | 引入新问题，返工 |

**「改对了」不能弥补「改多了」。** 用户需要的是对变更集的完全掌控——他心里有一个精确的改动清单，多出来的每一项都是他没审过的风险。

## 怎么做

动手前列一张清单，只对清单内的文件动手：

```
用户授权：改 install.sh
本次实际会动：install.sh（1 个文件）
不碰：README.md、其他脚本、配置
```

判断要不要顺带改：

| 情况 | 做法 |
|---|---|
| 顺带改的地方**不改就会出错** | 停下来告诉用户，问能不能一起改 |
| 顺带改只是**更一致/更整洁** | 不动，做完单独提一句"另外 XX 也可以一起改，要吗" |
| 拿不准算不算必须改 | 问。问一句成本远低于返工 |

**最小范围优先。** 能改 1 个文件解决的，不要动 2 个。

## 反例

- 用户说"把这个按钮的文案改了"，我把按钮样式也调了 —— 文案是授权范围，样式不是。
- 用户说"修一下这个 bug"，我把周边代码重构成了更优雅的写法 —— 修 bug 是授权范围，重构不是。
- 用户说"更新知识库文档"，我顺手新建了目录 —— 更新是授权范围，结构调整不是（见 [撤销改动必须用户授权](撤销改动必须用户授权.md)）。
