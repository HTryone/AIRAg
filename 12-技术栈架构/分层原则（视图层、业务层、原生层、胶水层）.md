# 分层原则（视图层、业务层、原生层、胶水层）

**结论**：业务逻辑堆进界面文件是多端项目烂掉的最快路径。四类职责各归各位，一套业务代码才能在网页 / 桌面 / 移动三端复用。

谁需要看这条：多端项目、或者界面文件已经写到几百行的人。

---

## 一、四层怎么分

| 层 | 放什么 | 不放什么 |
|---|---|---|
| **视图层**（Vue / React 组件） | 模板、视图状态、事件转发 | 业务逻辑 |
| **业务层**（.ts） | 传输、加密、状态机、流程编排 | 界面操作、DOM |
| **原生层**（Rust / Kotlin / Swift） | 文件系统、通知、窗口、系统调用 | 业务判断 |
| **命令层**（壳提供的通道） | 薄胶水，只做转发和类型转换 | 业务逻辑 |

命令层最容易变成垃圾场：**它应该薄到一眼能看完，只负责把前端的调用转给原生层。**

---

## 二、为什么必须分

| 好处 | 具体 |
|---|---|
| 一套业务代码三端复用 | 业务层不碰界面、不碰原生，换端不用重写 |
| 换壳不影响业务 | 原生实现换了，业务层不动 |
| 改界面不会带坏核心逻辑 | 视图层没有逻辑，怎么改都影响不到传输 |
| 可测试 | 业务层是纯代码，不依赖界面和平台 |

---

## 三、同类能力用同一套接口抽象

不同端的底层实现不一样，但对外的接口要一致。

典型做法：定义一个统一接口（例如"写入器"），各端各自实现，运行时判断当前环境选对应的实现。业务层只认接口，不关心当前跑在哪个端。

| 端 | 底层实现 | 对外接口 |
|---|---|---|
| 网页 | 文件系统访问接口 / 流式 / Blob | 同一套 |
| 桌面 | 原生文件写入 | 同一套 |
| 移动 | 媒体库 / 目录授权 / 文件描述符 | 同一套 |

业务层写一次，三端通用。

---

## 四、反例代价

**实测（2026-08-15，提交 a4a80d3）**：两个界面文件各接近 700 行，业务逻辑堆在里面。改一个按钮要把整个面板读完才能下手。

最后拆出约 340 行下沉到业务层，两个界面文件退化成纯视图（只剩模板 + 视图状态 + 状态条切换）。

判断要不要拆的标准：**这个文件里有没有"即使换一套界面也还要保留"的代码。** 有就该下沉。

---

## 五、避坑表

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 业务逻辑写进界面文件 | 文件膨胀到几百行，改一处要看全部 | 换界面也还要用的代码，一律下沉 |
| 命令层里写业务 | 壳和前端耦合，换端要重写 | 命令层只做转发 |
| 业务层直接调平台接口 | 换个端就跑不了 | 走统一接口，运行时选实现 |
| 视图状态塞进业务层 | 业务层被界面绑死 | 业务层只管流程和状态机，视图状态留在视图 |
| 各端各写一套业务 | 三份代码三份 bug | 抽象出共同接口，差异放进实现 |
| 拆完不验证 | 逻辑残留或漏拆 | 拆完全文搜索确认界面文件无逻辑残留，再跑类型检查 |
