# 多智能体并行工作流与验收

**结论**：大批量、可拆分的重复劳动，按**模块切成互不重叠的范围**分给多个子智能体并行跑；**主线程只负责拆活、定标准、验收**，自己从头干到尾反而更慢。

谁需要看这条：一次要改几十上百个文件、或要同时扫多台机器多个目录的人。

## 这是什么

一套「主线程编排 + 多个子智能体并行干活」的流程，覆盖四件事：什么活值得拆、怎么拆才不撞车、主线程怎么盯进度、交卷后怎么用机器校验验收。

## 一、什么活该用这套

| 适合 | 不适合 |
|---|---|
| 同一件事要在很多模块 / 很多机器上重复做 | 只有一两处改动 |
| 每个单元边界清楚，能说清"这个目录归你" | 各部分互相依赖，改动会串 |
| 有机器可校验的验收标准（语法检查、字符串比对、数量对账） | 只有"感觉写得好不好"这种标准 |

## 二、怎么拆

- **按模块 / 目录切，范围互斥**：每个子智能体只写自己那份目录，谁也不碰别人的。
- **单个子智能体的活以 20 分钟为限**，超了就再拆一层。
- **任务书必须写全六件**：目标、源路径与格式、怎么定位（搜索关键词）、输出位置与命名、禁止事项、验收标准。
- **能指路就不搬运**：工具、凭据、机器清单只写"在哪找"，不把内容抄进任务书（抄进去上下文会撑爆）。

## 三、主线程干什么

1. 先探测环境（连通性、版本、路径）并写进任务书 —— 别让子智能体摸黑试错。
2. 拆范围、写任务书、后台启动。
3. **看落盘文件判断进度**（数量 / 大小 / 时间戳），不空等交卷；卡住就催办（"每完成一个立刻落盘、缩小范围、限时"），还不行就拆出新任务派新的。
4. 交卷后**独立验收**（见下节）。

## 四、验收：机器校验，不轻信自述

| 校验项 | 做法 |
|---|---|
| 语法 / 可运行 | 全量跑一遍语法检查（不是抽查几个） |
| 内容没丢 | 原始字符串字面量逐条比对，一个都不能少 |
| 数量对得上 | 输入文件数 = 输出条目数（或明确记录跳过原因） |
| 不撞车 | 与兄弟任务的产出查重，重复的删掉，以"后交卷且校验更严"的为准 |
| 关键数字 | 主线程自己再取一次，和对方报的比对 |

**子智能体的"已完成"不算证据，校验脚本的输出才算。**

## 五、凭据与残留

- 默认**只读**：除任务书明确授权，不写、不改、不重启。
- 含密码的临时脚本**用完立刻覆盖清空再删除**。
- 交付后扫一遍工作目录，确认没有明文密码、密钥、token 残留。

## 六、常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 两个子智能体写同一目录 | 互相覆盖，白跑 | 范围必须互斥 |
| 任务书塞全文（命令、路径、凭据清单） | 上下文撑到几十万字符，对方开始瞎猜 | 只给路径，让它自己读 |
| 拿"已完成"当验收 | 数字对不上时已无法返工 | 机器校验 + 主线程复核 |
| 长时间卡住不干预 | 交卷时才发现方向错 | 看落盘进度，卡住就催办或拆 |
| 中间产物不清理 | 目录越堆越乱 | 用完即删 |
