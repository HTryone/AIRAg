# 多端同码架构（一份前端出 Web、桌面、移动）

**结论**：一套前端代码，同时产出网页版、桌面安装包、手机 App。关键在于**把壳和前端彻底分开**——前端能热更新，壳不能。

谁需要看这条：要把网页项目同时做成桌面端 / 移动端安装包的人。纯网页项目可以跳过。

---

## 一、这是什么

同一个前端仓库，出三种产物：

| 产物 | 怎么来的 | 用户拿到什么 |
|---|---|---|
| 网页版 | 前端直接部署到静态托管 | 一个网址 |
| 桌面端 | 前端产物 + 原生壳（Tauri）打包 | 一个安装包 |
| 移动端 | 同上，打安卓/iOS 包 | 一个 APK |

三种产物共用同一份前端代码和业务逻辑，只有最底层的原生能力不同。

---

## 二、结构怎么分

```
前端源码（Vue / React / 任意框架）
  ├── 网页产物   → 部署到静态托管
  └── 内嵌产物   → 被打进原生壳

原生壳（Rust / Kotlin / Swift）
  ├── Rust 层   → 窗口、命令、跨平台能力
  └── 平台层    → 安卓用 Kotlin，iOS 用 Swift
```

**原生壳只做三件事**：开窗口、给前端调原生能力的通道、打包分发。业务逻辑一律不进壳。

---

## 三、四条关键纪律

### 1. 前端走线上热更新，壳只能冷更新

前端部署在静态托管上，改了前端**重新部署即可，用户不用重装 App**。

壳（原生代码）改了**必须重新打包、用户重新安装**。

推论：能放进前端的改动就别放进壳。

### 2. 前端地址必须可配置，不能写死成打包产物路径

壳里加载哪个前端地址，必须写成配置项。

写死的后果：想把 App 指向线上地址（或换一个部署环境），就得重新打包、重新发版。

做法：配置文件里放地址，不同环境用不同配置文件覆盖。

### 3. 调试和发布分开

| 场景 | 壳加载哪里 |
|---|---|
| 开发调试 | 本地开发服务器（如 `http://localhost:3002`） |
| 发布 | 线上地址 |

用两份配置区分，不要每次打包前手动改地址。实测做法：桌面端配置文件覆盖为 3002 端口，移动端覆盖为 3003 端口（两端同时开调试不冲突），发布配置统一指向线上地址。

### 4. 一条命令出全部产物，版本号单点

构建脚本一条命令产出所有平台的包，版本号只在一个地方写，由脚本同步到各个配置文件。

禁止手动去改每一处版本号 —— 漏改一处就会打出版本不一致的包。

---

## 四、从零怎么搭

1. **先有能独立运行的网页版** —— 前端能单独部署、单独访问，不依赖壳
2. **接原生壳** —— 初始化壳工程，让它加载本地开发服务器地址
3. **配调试/发布两份配置** —— 调试指向本地，发布指向线上
4. **写构建脚本** —— 一条命令出全部产物，版本号参数化
5. **验证** —— 打完包必须实际装一次，确认壳加载的是预期地址

---

## 五、什么时候该上桌面壳

浏览器够用时不要上壳。上壳的典型理由：

| 场景 | 说明 |
|---|---|
| 浏览器不支持某个能力 | 例如文件系统访问接口在部分浏览器没有，用壳补上 |
| 需要脱离浏览器运行 | 用户不想开浏览器 |
| 需要系统集成 | 通知栏、开机启动、文件关联 |

**壳是用来补浏览器缺的能力的，不是用来重写业务的。** 业务代码仍然共用。

---

## 六、避坑表

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 前端地址写死成打包产物路径 | 换环境就要重打包重发版 | 地址配置化，调试/发布两份配置 |
| 业务逻辑写进壳 | 改一点业务就要发版，用户重装 | 壳只做窗口和通道 |
| 手动改各处版本号 | 打出版本不一致的包 | 版本号单点，脚本同步 |
| 只打一个平台就交付 | 另一个平台的包可能是坏的 | 全平台都打一遍 |
| 以为改了前端用户就能看到，结果改的是壳 | 用户那边的 App 毫无变化 | 先分清这次改的是哪一层 |
| 覆盖安装验证原生改动 | 覆盖安装不会重新触发授权、不会刷新壳资源，看到的是假象 | 验证壳改动必须卸载重装 |
