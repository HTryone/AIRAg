# 性能问题怎么分层定位

**核心结论**：性能问题没有报错、没有堆栈可看，只能靠测。办法是把整条链路拆成几段，逐段单独计时，先找到最慢那一段，再针对它查原因。

---

## 一、这类问题为什么难查

功能出错了有报错信息，性能问题只有一句"慢"。而且"慢"是相对的——不知道正常该多快，就没法判断现在是bug还是本来就这个速度。

所以第一步永远不是改，是**测出每段各自多快**。

---

## 二、先分清是哪种慢

两种慢的查法完全不同：

| 现象 | 性质 | 方向 |
|---|---|---|
| 一直很慢，但速度稳定 | 吞吐上限不够 | 找天花板在哪一段 |
| 开始快，越跑越慢 | 有东西在累积 | 找泄漏、缓存膨胀、句柄未释放 |
| 忽快忽慢 | 缓冲或批处理 | 看是不是成批转发 / 缓冲满了再刷 |
| 偶尔卡一下再继续 | 等待或重试 | 找超时、重试、GC |

这四种要靠**连续观察**才能分清。只看一次读数会误判——取 10 次读数看走势，比看一次峰值有用得多。

**看均值，不看峰值。** 峰值只说明"最好能到多少"，均值才代表实际体验。

---

## 三、拆链路

数据从产生到落地，中间必然经过若干段。每一段都有可能成为瓶颈。典型的段：

```
读源 → 处理/加工 → 传输 → 落盘 → 确认/回执
```

做法：在每段的入口和出口打时间戳，得到每段的耗时。

```bash
t0 = 进入本段
t1 = 离开本段
本段耗时 = t1 - t0
本段速度 = 数据量 / 本段耗时
```

**不要只看端到端总时间。** 总时间是 100 秒，可能是某一段占了 95 秒，也可能是五段各占 20 秒——这两种情况改法完全不同。

---

## 四、三个定位手段

### 手段一：分段计时（最基础）

在每段进出口埋点，跑一次，把每段的耗时和速度列成表格。

| 段 | 耗时 | 速度 |
|---|---|---|
| 读源 | 2s | 50 MB/s |
| 处理 | 5s | 20 MB/s |
| 传输 | 90s | 1.1 MB/s ← 瓶颈在这 |
| 落盘 | 3s | 33 MB/s |

一眼就能看出该查哪段。

### 手段二：摘除法（最可靠）

怀疑某一段，就把**它后面所有段摘掉**，只跑到它为止，看速度有没有变化。

- 摘掉后速度暴涨 → 瓶颈在被摘掉的部分
- 摘掉后速度没变 → 瓶颈在前面，别再查后面了

这是唯一能实锤的手段。分段计时可能因为打点位置不对而误判，摘除法不会。

### 手段三：加倍喂料法（判定天花板）

把**上一段的供给速度提高**（加并发、加缓冲、换更快的源），看下一段跟不跟得上：

- 下游速度跟着涨 → 是供给不足，继续优化上游
- 下游速度纹丝不动 → **下游就是天花板**，上游做得再快也没用

```
案例：2026-08-22 一次文件传输，落盘实测均值 3.5 MB/s。
把解密并发从 1 提到 3（上游快了 3 倍），落盘速度没有任何变化。
判定：落盘是天花板，上游优化全部无效。该项改动随后回退。
```

---

## 五、关键判断：这是天花板还是 bug

这是性能排查里最重要的一次判断，判断错就会做一堆无用功。

| 特征 | 天花板 | bug |
|---|---|---|
| 速度表现 | 稳在某个值附近，波动小 | 随时间下降，或忽高忽低 |
| 调参数 | 怎么调都不涨 | 换个参数就明显变化 |
| 加倍喂料 | 下游纹丝不动 | 下游跟着涨 |
| 换环境 | 换硬件 / 换平台就涨 | 换环境也一样 |
| 资源占用 | 磁盘或 CPU 已经跑满 | 资源还很闲 |

**确认是天花板之后就该停手**，转而去查"为什么这段这么慢"，而不是继续优化其他段。

常见的天花板来源：

| 层 | 典型天花板 |
|---|---|
| 磁盘 | 随机写、小文件太多、写入时附带索引/元数据更新、网络文件系统 |
| CPU | 单线程跑满、加密或压缩算得慢 |
| 网络 | 单条连接限速、走了中继、中间节点整段缓冲 |
| 内存 | 频繁 GC、缓存反复失效 |

## 六、先测个基准，再下结论

不知道"正常该多快"，就没法判断现在慢不慢。用现成的工具测一下裸速度：

**磁盘（Linux）**

```bash
dd if=/dev/zero of=./speedtest bs=1M count=256 oflag=direct    # 写入速度
dd if=./speedtest of=/dev/null bs=1M                            # 读取速度
```

**磁盘（Windows PowerShell）**

```powershell
winsat disk -drive c
```

**网络（两端都要装）**

```bash
iperf3 -s              # 服务端
iperf3 -c 服务端地址    # 客户端
```

**单线程 CPU**

跑一段纯计算，看耗时，跟预期比。

测出来的数是**参照系**：应用层跑出来的速度如果已经接近裸盘 / 裸网速度，说明没什么可优化的了，再调就是在浪费时间。

---

## 七、止损线

性能优化很容易陷进去——总想着"再试一个参数说不定就快了"。定个硬线：

1. **连续 2-3 次调参，速度没有明显变化 → 停手**，回去重新定位
2. 已经确认是天花板 → 停手，写进文档，别再试
3. 每次只改一处，改完立刻复测，不改完一堆再测

见 [改之前先拿证据](改之前先拿证据.md)：一次改一处，连续几次无效就停下来重新找根因。

---

## 八、避坑表

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 只看界面上显示的速率 | 那个数字统计的是网络口径还是落盘口径，不确认就当成落盘速度，结论全错 | 先确认这个数字是哪一段的 |
| 盲目加并发 | 并发只解决"等待"，不解决吞吐上限 | 先用加倍喂料法确认是不是供给不足 |
| 换个参数没涨，继续换下一个 | 在错误的段上空转 | 2-3 次无效就重新定位 |
| 不测基准就下结论 | 不知道正常该多快 | 先测裸盘 / 裸网速度当参照 |
| 拿峰值说事 | 峰值不代表实际体验 | 看均值和波动 |
| 把平台天花板当 bug 修 | 改了没用，改多了还引入新问题 | 按第五节的表判定性质 |
| 一次性改五处再测 | 不知道是哪处起作用 | 一次改一处，改完就测 |
| 排查时顺手改别的 | 引入新变量，前功尽弃 | 排查阶段只加打点，不改逻辑 |
