# 内存持续增长怎么查

**结论**：内存一路涨到崩溃，不要靠"觉得是哪里缓存了"去改。先测出**涨在哪个阶段**，再定位到具体对象，改完必须复测。

用户环境实测：ArkPulse / FlashDrop 浏览器端批量解密时，Worker 出现内存累积导致崩溃，用代码级打点定位。

---

## 一、先确认是不是真泄漏

内存涨有两种，处理方式完全不同：

| 类型 | 曲线形状 | 说明 |
|---|---|---|
| **泄漏** | 一路上升，从不回落 | 对象始终被引用，回收不掉 |
| **高峰** | 涨到顶后回落 | 只是峰值需要内存，不算泄漏 |

判定方法：跑完一轮后强制回收一次，看内存掉不掉。

浏览器 DevTools → Memory → 点垃圾桶图标（强制 GC）→ 再取样。掉下来 = 不是泄漏，只是峰值高；不下来 = 泄漏。

Node.js：

```bash
node --expose-gc your-script.js
```

代码里在阶段结束后调 `global.gc()` 再打点。

**没做这一步就动手改，等于瞎猜。**

---

## 二、定位涨在哪个阶段

把流程切成若干段，每段结束打一个点：

```javascript
function mark(label) {
  const used = performance.memory.usedJSHeapSize / 1024 / 1024;
  console.log(`[${label}] ${used.toFixed(1)} MB`);
}

mark('开始');
await 读取阶段();
mark('读取完成');
await 解密阶段();
mark('解密完成');
await 写出阶段();
mark('写出完成');
```

跑一遍看输出：

```
[开始] 12.4 MB
[读取完成] 480.2 MB     ← 涨在这
[解密完成] 495.8 MB
[写出完成] 502.1 MB
```

内存是在**读取阶段**涨起来的，跟解密没关系。没有这个数据，很容易往解密算法上找原因。

`performance.memory` 只在 Chrome 有，且需要 `--enable-precise-memory-info` 才精确。Node.js 用 `process.memoryUsage().heapUsed`。

## 三、四个常见来源

按实际出现频率排：

### 1. 数组/Map 只增不减

最常见。攒了一堆结果但从不清理。

```javascript
const results = [];
for (const item of items) {
  results.push(await process(item));  // 一万个文件就攒一万个结果
}
```

改法：处理完就用掉，不要攒；或者按批处理完清空 `results.length = 0`。

### 2. 大对象被闭包捕获

```javascript
function makeHandler(bigBuffer) {
  return () => {
    // 只要这个函数还活着，bigBuffer 就不会被回收
    console.log(bigBuffer.length);
  };
}
```

改法：闭包里只捕获需要的小数据，不用整个大对象。

### 3. 事件监听没解绑

```javascript
worker.addEventListener('message', handler);  // 用完没 removeEventListener
```

改法：用 `AbortController` 统一解绑，或显式 `removeEventListener`。

### 4. Blob / ArrayBuffer 没释放

浏览器里 Blob 用 URL.createObjectURL 创建的地址，必须 `URL.revokeObjectURL` 释放：

```javascript
const url = URL.createObjectURL(blob);
// 用完
URL.revokeObjectURL(url);
```

不释放，这个 Blob 会一直留在内存里直到页面关闭。

## 四、二分定位

打点已经定位到阶段，但阶段内代码还是很多时，用二分：

1. 把阶段后半段注释掉，看内存还涨不涨
2. 不涨了 → 问题在后半段；还涨 → 在前半段
3. 对有问题的那半段重复，直到定位到具体几行

比通读代码快得多，而且不依赖"我觉得这里有问题"。

---

## 五、改完必须复测

改完再跑一遍同样的打点，对比数字：

| | 改前 | 改后 |
|---|---|---|
| 读取完成 | 480.2 MB | 45.6 MB |
| 解密完成 | 495.8 MB | 61.2 MB |
| 写出完成 | 502.1 MB | 52.8 MB |

**没有前后对比数字，不能说修好了。** 感觉变快了不算证据。

如果改完数字没变，说明没找到真正的来源，回到第二节重新打点，不要继续改下一处。

---

## 六、止损线

| 条件 | 动作 |
|---|---|
| 连续 2 处修改都没有让数字变化 | 停止，回到打点重新定位 |
| 打点显示内存涨在第三方库内部 | 停止改自己的代码，查库的用法或换方案 |
| 已降到可接受水位 | 停止，不要为了更好看继续改 |

见 [改之前先拿证据](改之前先拿证据.md)。

---

## 七、常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 不强制 GC 就判断泄漏 | 把正常峰值当泄漏，白改一通 | 先 GC 再取样 |
| 凭"这里可能缓存了"去改 | 改错地方，引入新问题 | 打点看数字 |
| 一次改好几处 | 有效果也不知道是谁的功劳 | 一次改一处，改完复测 |
| 只测小数据量 | 小样本看不出增长，上线就崩 | 用真实量级的数据测 |
| 改完不复测 | 不知道到底修没修好 | 必须有前后对比数字 |
| 在开发环境测生产数据量 | 开发环境内存限制不同 | 尽量贴近真实环境 |
