# 拿到共享代码要整份搬：不删改逻辑，用完原样归还

**结论**：借别人的代码**整份原样搬进来**（一份不动逻辑的副本），**用完把文件删干净、还原到搬之前的目录状态**；不要"挑一部分搬"、不要"顺手优化"、不要留在项目里当残留。

## 为什么

2026-10-16 接手一个 Laravel 仓库时明确写了这条纪律：共享代码整份搬入，用完删除、原样归还仓库。理由有三条：

1. **挑着搬会缺依赖**：片段之间互相引用，搬一半必然少东西，又不容易发现。
2. **顺手改会污染**：改过的副本已经不是"借用"，说不清是谁的问题。
3. **留着会误伤下次**：下次再搬，目录里已经有一份"看起来一样但被改过"的东西，很难判断该用哪份。

## 怎么做

```text
搬之前：记下目标目录当前的文件清单（或先确认它是空的）
搬：整目录复制，不裁剪、不改名、不改内容
用：只在副本上读/跑
归还：删掉整份副本，再核对目标目录的文件清单与搬之前一致
```

| 步骤 | 判据 |
|---|---|
| 搬入 | 副本的文件数与源一致 |
| 使用 | 副本内没有任何被改动的文件（可跑一次哈希比对） |
| 归还 | 目标目录回到搬之前的状态（文件清单一致） |

## 反例

- 「我只要其中三个文件，先拷三个试试」→ 跑起来报缺模块，再回头补，补的过程中很可能把周边也改了。
- 「这份副本顺手修了个小 bug」→ 归还时说不清这个修改该不该带回去。
- 「用完忘了删」→ 下次搬进来新旧两份混在一起。
